# dedupe 自動化 — 「好みのバージョンを絶対に消さない」自動整理 要件定義

作成: 2026-07-19（Claude Code / Opus 4.8）。親要件 [dedupe-requirements.md](dedupe-requirements.md) の拡張。
**本ドキュメントは要件定義であり、実装はまだ行っていない。**

> 親要件 §7「やらないこと」は "自動判断・自動削除" を禁じ、§2 は "nightly 見張り = 後で検討" とした。
> 本ドキュメントは本人決定により、**「音が完全に同一と証明できるものだけ」に限定して**その禁を解く。
> 別バージョン（feat / with / Remaster / Live / Acoustic 等）の判断は従来どおり100%手動のまま。

## 0. 最上位の不変条件（これを破る実装は不可）

**あなたが好むかもしれないバージョンが、自動処理で消えることは絶対に起きない。**

この保証は「気をつける」ではなく、下記の適格判定（§2）を満たすグループ**以外には自動削除経路が
コード上存在しない**ことで担保する。判定は「同じ録音だと ISRC で証明でき、かつ別編集の疑いが
数値・語彙のどちらでも一切ない」ものだけを通す。少しでも疑わしいものは自動対象から**落として手動へ回す**
（フォールバックは常に「手動レビュー」であって「自動削除」ではない）。

## 1. 自動 / 手動の二分

| 区分 | 対象 | 処理 |
|---|---|---|
| **自動整理（本要件）** | 音が同一と証明できる重複（同一 ISRC・秒数ほぼ一致・版差表記なし） | §3 の優先順で1つ残し、残りを自動削除（通知＋undo付き） |
| **手動レビュー（親要件のまま）** | 別バージョン・別録音・少しでも疑わしいもの | ダッシュボードの選択 UI で本人が残す版を選ぶ。自動処理は一切触らない |

## 2. 自動削除の適格判定（AND 条件・全て満たすグループのみ）

グループが以下を**すべて**満たすときだけ自動整理の対象にする。1つでも外れたら手動へ。

1. **Tier B である**: グループの全メンバーが**同一かつ非空の ISRC** を共有する。
   ISRC は録音を一意に識別する国際規格 ⇒ 一致は「同じ録音」を意味する。Tier C（ISRC 不一致・
   タイトル一致のみ）は**永久に対象外**（feat/Remaster/別テイクがここに入るため）。
2. **秒数差 ≤ 3.0 秒**: メンバー間の `duration_ms` の最大差が 3000ms 以内。
   同一 ISRC でも秒数が大きくズレるものは、レーベルが別編集に ISRC を使い回した疑いがあるため落とす。
   （実データ: "Everybody Loves Me" は同一 ISRC でも Δ4.6s ⇒ 自動対象から除外し手動へ）
3. **版差キーワードを含む差分がない**: メンバーのタイトルを NFKC・小文字化して比較したとき、
   差分に版差語（`feat` `ft` `with` `remix` `acoustic` `live` `remaster` `version` `taylor's version`
   `sped up` `slowed` `edit` `mono` `stereo` `deluxe` `instrumental` 等＝`dedupe._VERSION_WORD`）を
   **一切含まない**こと。含めば同一 ISRC でも手動へ回す（あなたの「feat で重複しているのだけ見たい」を明文化）。
   ※ サウンドトラック等の非版差タグ（例: "Nobody" ↔ "Nobody - from Kaiju No. 8"）は版差語でないので自動可。
4. **`dedupe_keep.json` に無い**: 過去に「両方残す(k)」と決めたグループは、あなたの明示的意思として
   **常に自動より優先**し、二度と自動対象にしない。
5. **削除後も必ず1曲以上残る**: 適格でも残す1曲を確定できないグループ（判定不能）は落とす。全消しは構造的に起きない。

## 3. 残す1曲の決定ルール（決定論的・あなたの方針に一致）

適格グループでは、次の優先順で1曲を残し、それ以外を削除する:

1. **アルバム種別**: `album` > `single` > `compilation`（本人確定・2026-07-19）。
   ＝「album にあるなら album、無ければ single、それも無ければ compilation（ベスト盤/寄せ集め）」。
   実装は keep 用に `{album:0, single:1, compilation:2}` を用いる（**dedupe.py の表示用 `_album_rank`
   `{album:0, compilation:1, single:2}` とは別の順位**。表示ソートは変えず、自動 keep 選択のみこの順位）。
2. 同点なら **人気度 `popularity` 降順**
3. さらに同点なら **収録プレイリスト数が多い方**（削除による波及を最小化）
4. 最後に **track_id 昇順**（完全に決定論的にして再現性を担保）

同一 ISRC＝音は同一なので、どれを残しても再生される音は変わらない。順位は「表示上どの版を代表にするか」の
決定にすぎず、聴取内容の損失は原理的に発生しない。

## 4. 実行フロー（nightly 組み込み）

1. 実行位置: nightly の **inbox → sync → sort の後**（在籍が整った状態でスキャン）。
2. 既存 `dedupe.scan` で全管理プレイリストを横断スキャン（読み取り専用・追加 API コストゼロ）。
3. §2 の適格判定で**自動対象グループのみ**を抽出し、§3 で各グループの `keep`/`remove` を自動生成。
4. 適用は**既存の `siteops.op_dedupe_apply` をそのまま再利用**する（新しい削除経路を作らない）:
   - undo を**先に**確定してから削除（記録できなければ削除しない）。
   - 全管理プレイリストから同時に remove-all-occurrences（§6 の sync 整合・残留防止）。
5. **何を消したかをホームタブから見られるようにする**（§4.1）。＝「気づいたら消えていた」を防ぐ確認経路。
6. dry-run（`DRY_RUN=1`）では変更系 API を1回も呼ばない。scan と「削除予定」の出力だけ。

### 4.1 ホームタブでの可視化

- nightly の実行履歴は既に `inbox / sync / sort / archive` の各ステップをホームで表示し、タップで内訳
  モーダルを開ける（`sitegen.build_run_record` の `steps` / `detail`）。**自動 dedupe を5つ目のステップとして
  この仕組みに乗せる**（新しい UI 経路を作らず既存の内訳モーダルを流用）。
- ステップ要約: 「自動整理: N曲を削除（Mグループ）」。0件の晩は他ステップ同様「変更なし」で出す。
- 内訳（モーダル）で1グループ1行、各行に **残した版 / 消した版・その理由（同一 ISRC・Δ○秒）/ undo ID** を表示。
  undo ID を載せることで、驚いたら siteops の undo でそのまま戻せる導線にする。
- データは自前の状態ファイル（例: `data/` 配下の run 内訳）に載せるだけで、外部サービス（Discord 等）へは送らない。
  **本プロジェクトは個人利用。通知や共有の外部連携は要件に含めない。**

## 5. 非機能・安全要件

1. **無条件の自動削除経路を作らない**。自動削除は §2 の適格判定を通ったグループにのみ到達する。
2. ヘッドレスでも動くのは自動整理（適格グループの一括削除）まで。**手動レビュー用の対話/選択は自動化に含めない**。
3. 全ての自動削除は undo 可能（既存 undo 基盤・track_id 再追加で完全復元。並びは sort が翌晩直す）。
4. 認証/スコープが無い・スキャン失敗時は**何もせず正常終了**（nightly 本体を落とさない）。
5. exit code は既存規約（0/1/3）。スコープは既存 inbox と共用し新規認証を発生させない。
6. archive プレイリストには触れない。Japanese ⇄ Western 間の誤振り分けは対象外（分類検証の別件）。

## 6. sync / sort との整合（親要件 §6 を継承）

- 同一曲の**全出現箇所を1グループにまとめ、削除も全箇所同時**に実行（Western だけ消して AP に残す、
  AP だけ消して Western からも消える、のどちらも防ぐ）。
- 削除翌 nightly の sync は「state にあるが AP に無い」を検出→既に無いので no-op→state 収束。これを受け入れ基準に含む。

## 7. 受け入れ基準（実データ・Western Musics で検証）

1. 同一 ISRC・Δ≤3s・版差語なしの **18グループ**が §3 の優先順（album > single > compilation）で自動整理される。
   特に "Moves Like Jagger"（album `Hands All Over` と compilation `Singles`）では **album 版が残る**。
2. **"Everybody Loves Me"**（同一 ISRC だが Δ4.6s）は**自動で触られず**、手動レビューに残る。
3. Tier C の **3グループ**（"I Ain't Worried" 別編集 / "Run (with Mariah Angeliq)" / "Viva La Vida" リマスター違い）は
   **自動で触られない**。
4. `dedupe_keep.json` に登録済みのグループは、適格でも自動で触られない。
5. dry-run 実行時、変更系 API が1回も呼ばれていない（削除予定の一覧だけ出る）。
6. 自動削除発生時、**ホームタブの実行履歴に dedupe ステップが出て、内訳に「残した版/消した版/理由/undo ID」が並ぶ**。
   外部サービスへの送信は一切発生しない。
7. 自動削除後の翌 nightly が、失敗・意図しない削除なしで完走する（no-op 収束）。
8. undo ID から取り消すと、削除された全出現箇所が復元される。

## 8. 関連して直すべき既存バグ（本要件のスコープだが独立に実施可）

- `siteops.op_classify_apply`（[siteops.py](../siteops.py) 内）が、先日修正したのと**同じ壊れた API**
  `current_user_saved_tracks_delete` を1件ずつ呼んでいる。今回 `core.remove_saved_in_batches`
  （`DELETE /me/tracks` 直叩き）に統一済みなので、そちらへ差し替える。1件呼びのため即 400 にはならないが、
  同一の根本原因（spotipy 2.26 の `me/library` 経路）なので予防的に直す。

## 9. 本要件で「やらないこと」

- Tier C（別バージョン）の自動判断・自動削除（＝本要件の存在意義そのものを侵すので永久に不可）。
- 秒数差 >3s・版差語ありのグループの自動処理。
- album 同士の重複で「どのアルバムを代表にするか」に本人の嗜好を反映する自動学習（§3 の決定論で固定）。
  もし特定アルバムを優先したい要望が出たら、その時に §3 に例外ルールを足す（今は入れない）。
