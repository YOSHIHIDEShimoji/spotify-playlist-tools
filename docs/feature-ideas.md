# 機能アイデア集 — Spotify 生活をより楽しくする25案

作成: 2026-07-14（Claude Code / Fable 5）
性質: ブレインストーミング。実装約束ではない。気に入ったものだけ Issue 化して育てる。

このプロジェクトは「コードが日常生活に直接効いている唯一のもの」。だから評価軸は
機能の高度さではなく **毎日の嬉しさ ÷ 維持コスト**。夜間バッチ・Issue チャネル・
分類キャッシュ・Top50アーカイブという**既にある資産に複利で乗る**案を優先して並べた。

---

## 0. 前提 — 使える API / 使えない API（2026-07-14 実測）

このアプリ（2025年5月作成）で実際に叩いて確認した結果:

| API | 状態 | 意味 |
|---|---|---|
| `audio_features`（BPM/energy/danceability） | ❌ **403** | テンポ・ムード系の案は Spotify 単体では作れない |
| `recommendations`（公式レコメンド） | ❌ **404** | 公式おすすめ取得は不可。発見系は自作するしかない |
| `related_artists` | ❌ **404** | 類似アーティストも自作（Gemini 等）で代替 |
| `artist_albums`（アーティストの新リリース） | ✅ OK | **新譜検知が作れる** |
| `new_releases`（国別新譜棚） | ✅ OK | JP の新譜棚を巡回できる |
| track detail（`available_markets` 等） | ✅ OK | 「灰色になった曲」検知が作れる |
| `search` / playlist cover | ✅ OK | 名前→実在確認、カバー画像取得 |
| `recently_played` / `top_artists` | ⚠️ **要スコープ追加** | 聴取履歴系は一度だけ再認証が必要（下記） |

**聴取履歴系を解放する1回だけの作業:** `core.py` の SCOPE に
`user-read-recently-played user-top-read` を足してローカルで対話再認証 →
`gh secret set SPOTIFY_TOKEN_CACHE < .cache-spotify`。これで A 系統の案が全部動く。

> 教訓として: 「公式レコメンドが死んでいる」のは制約ではなく方向性。
> **自分の聴取データ＋自分の判定基準で作る「自家製レコメンド」**の方が、
> このプロジェクトの思想（自分の音楽生活を自分のコードで運転する）に合っている。

## A. 聴取ログ基盤 — ほぼ全部の案を解放するイネーブラー

### A-1. 聴取履歴の永続蓄積（最重要・これが土台）🏗️

`recently_played` は**直近50件しか取れない**。つまり今この瞬間も履歴は流れて消えている。
nightly に「取得 → `listening_log/YYYY-MM.jsonl` に追記 → commit」を足すだけで、
**自分の全聴取履歴が Git に貯まり始める**。1日でも早く始めるほど資産が増える。

- 実装: `played_at` をキーに重複排除して追記。1ステップ20行程度
- 補足: 聴く量が多い日は50件を超えて溢れる。Actions の cron を1日3〜4回に増やせばほぼ取りこぼさない（無料枠で余裕）
- **工数: 小 / 嬉しさ: 直接は地味。ただし A-2〜A-6, C-3, D 系の全案がこれに依存**

### A-2. 月次リキャップ「自家製 Wrapped」📊

Spotify Wrapped は年1回だが、データが手元にあれば**毎月**作れる。
月初の nightly が先月分を集計して Issue に投稿:
今月のトップ10曲/アーティスト・総再生時間・新規発見数・邦楽/洋楽比率・先月比。

- 実装: A-1 の JSONL を集計するだけ。グラフは Issue 内の Mermaid か SVG 生成
- **工数: 小〜中 / 嬉しさ: 大（毎月1日が楽しみになる）**

### A-3. 「1年前の今日」タイムマシンプレイリスト 🕰️

`Time Machine` という固定プレイリストを作り、nightly が「去年の同じ週によく聴いていた曲」で
中身を毎週入れ替える。聴取ログが2年分貯まると「2年前の今日」も選べる。
**音楽は記憶のインデックス**。去年の試験期間に聴いていた曲が流れてくる体験は強い。

- 実装: A-1 のログを日付範囲でフィルタ → 再生回数順 → replace。sort.py の置換ロジックを再利用
- **工数: 小（A-1 の後なら）/ 嬉しさ: 大。個人的イチオシ**

### A-4. 殿堂入り/ランク外の変動検知 🏆

`top_artists`（short_term = 直近4週）を毎週スナップショットし、先週比で
「LANY が初のトップ5入り」「Maroon 5 が圏外へ」を週次 Issue で報告。
自分の好みの変化は本人が一番気づかない。

- **工数: 小 / 嬉しさ: 中（週次の読み物として）**

### A-5. リピート検知「今週のヘビロテ」🔁

同じ曲を1日に3回以上聴いた日を検知して記録。「2026年7月、あなたは『orbit』を1日9回聴いた」
という記録は、その時期の自分の状態のログでもある。A-2 の月次リキャップに1コーナー追加する形。

- **工数: 極小（A-2 に相乗り）/ 嬉しさ: 中**

### A-6. 聴取ダッシュボード（GitHub Pages）📈

listening_log から静的 HTML を生成して GitHub Pages で公開。月別聴取時間の推移・
時間帯ヒートマップ（朝型がデータで見える）・邦楽/洋楽比率の推移・アーティスト変遷。
リポジトリが public なので「公開される」点だけ認識しておく（好みの公開は既に許容済み）。

- 実装: nightly の最後に JSON 集計 → Chart.js の静的ページを docs/ か gh-pages に commit
- **工数: 中 / 嬉しさ: 中〜大（見た目が楽しい。友達に見せられる）**

## B. 発見系 — 死んだ公式レコメンドの自家製代替

### B-1. 新譜ウォッチ 🚨（即効性 No.1）

sync.txt + inbox.txt の登録アーティスト（現在12組）の `artist_albums` を nightly で監視し、
新リリースを検知したら **`New Releases` プレイリストに自動追加 + Issue 通知**。
「好きなアーティストの新譜を出た日に知る」は音楽生活の基本体験なのに、
Spotify の通知は気まぐれ。これを確実にする。

- 実装: 前回見た album id 集合を state に持ち、差分を検知。既存の state パターンそのまま
- **工数: 小 / 嬉しさ: 大。最初に作るならこれ**

### B-2. Top50 アーカイブの「後追い発掘」⛏️

archive には「過去に Top50 入りした全曲」が貯まり続けている（現在の唯一の用途は蓄積のみ）。
この**眠っている資産**を掘る: 月次で「アーカイブにあるが自分のプレイリストに1曲もないアーティスト」を
抽出し、Gemini に「この人の好み（分類キャッシュ＋トップアーティスト）に合いそうか」を判定させ、
上位5曲だけ `Discovery` プレイリストに置く。**聴いて気に入れば Like するだけ**で、
既存の inbox パイプラインが勝手に振り分ける — 発見から定着まで全自動接続。

- **工数: 中 / 嬉しさ: 大（自家製レコメンドの本命）**

### B-3. Gemini 類似アーティスト開拓 🧭

`related_artists` の代替。月1で Gemini に「Henry Moodie, LANY, OneRepublic ... を聴く人が
まだ聴いていなさそうなアーティストを5組」と聞き、`search` で実在確認 →
各2曲だけ Discovery に追加。ハルシネーションは search 照合で弾く。

- **工数: 小〜中 / 嬉しさ: 中（B-2 と同じ Discovery 枠に相乗り）**

### B-4. フィーチャリング検知 🤝

登録アーティストの `appears_on`（客演・コラボ）を監視。本人名義でないリリースは
見逃しやすい。B-1 の実装に `include_groups="appears_on"` を足すだけ。

- **工数: 極小（B-1 に相乗り）/ 嬉しさ: 中**

### B-5. JP 新譜棚の自動選別

`new_releases(country="JP")` を週1で取得し、分類キャッシュ＋Gemini で「好みに合いそうな邦楽新譜」
だけ Discovery へ。邦楽側の発見が今は完全に手動なのを補う。

- **工数: 中 / 嬉しさ: 中**

## C. プレイリスト衛生 — 既存パイプラインの自然な延長

### C-1. 重複・別バージョン検出 🧹

Western Musics は451曲。同じ曲の Single 版と Album 版、Remaster が混ざっているはず。
ISRC 一致 or 正規化タイトル＋アーティスト一致で検出し、**Issue で報告のみ**（自動削除はしない。
どちらを残すかは人間の判断）。既存の unknown-tracks Issue と同じ運用パターン。

- **工数: 小 / 嬉しさ: 中（一度きれいにすると気持ちいい系）**

### C-2. 灰色曲（再生不能）検知 ⚰️

配信停止でプレイリスト内に「灰色の曲」が静かに増えていく問題。`available_markets` が
空/JP 非含有になった曲を nightly で検知して Issue 報告。「いつの間にか聴けなくなっていた」を
「消えた日に知る」に変える。同一 ISRC の別リリースが検索で見つかれば差し替え候補も添える。

- **工数: 小 / 嬉しさ: 中〜大（発生頻度は低いが、起きたとき確実に助かる）**

### C-3. 「もう聴いてない曲」の棚卸し提案 🍂

A-1 のログと照合し、半年間再生ゼロの曲を年2回 Issue でリストアップ。
削除はしない — `Vault`（倉庫プレイリスト）への移動を**提案**するだけ。
プレイリストは「今の自分」を映す場所、Vault は「歴史」を守る場所、と役割を分ける。

- **工数: 小（A-1 依存）/ 嬉しさ: 中**

### C-4. Japanese 側の sync 対称化

sync.py の自動検出（20曲でアーティスト別プレイリスト自動作成）は Western 専用。
Japanese Musics にも同じ仕組みを適用すれば、邦楽側も自動で育つ。
sync.txt に `SOURCE` を複数書ける形式にするだけで、コードはほぼ既存のまま。

- **工数: 小 / 嬉しさ: 中（邦楽をよく聴くなら大）**

### C-5. コラボ曲の全 AP 配置

現在は「双方向削除で片側の AP に残留する」を仕様と割り切っている（bugs §10）。
逆に「登録アーティスト全員の AP に配置する」を明示仕様にすれば、
Charlie Puth × Ed Sheeran のコラボが両方のプレイリストから聴ける。

- **工数: 極小 / 嬉しさ: 小〜中**

## D. Issue チャネルの進化 — 通知から対話へ

### D-1. unknown 曲を Issue コメントで振り分け 💬（fable5 的イチオシ設計）

今: unknown 曲は Issue に載って、お気に入りに残るだけ。
提案: **Issue のコメントに「japanese」or「western」と書くと、次の nightly がコメントを読んで
振り分け実行 + 分類キャッシュに学習**する。GitHub Issue が人間⇔bot の双方向チャネルになり、
スマホから通知を見る→その場で1語返信→完了、という UX になる。
これは将来の AI 組織（Issue をエージェントが拾う世界）の最小プロトタイプでもある。

- 実装: nightly 冒頭で `gh issue view --comments` を読んでコマンドをパース
- **工数: 中 / 嬉しさ: 大（毎回の摩擦が消える + 思想的に美しい）**

### D-2. 週次ダイジェスト Issue 📰

毎週月曜の朝、1本の Issue に先週のまとめ: 振り分け実績・新譜・ヘビロテ・トップ変動・
灰色曲。**Issue は増やしすぎると通知が騒音になる**ので、B/C 系の報告は
この週次ダイジェストに集約し、即時性が要る失敗通知だけ個別 Issue のままにする。

- **工数: 小 / 嬉しさ: 中（他の案の「置き場」としての価値が大きい）**

### D-3. 朝の「今日の1曲」☀️

nightly の最後に、アーカイブか聴取ログから Gemini が1曲選んで一言添える
（「1年前の今週、9回聴いていた曲」「Top50 に3日だけいた隠れた曲」など選定理由つき）。
D-2 の週次に入れるか、専用の固定 Issue に毎日コメント追記する形。

- **工数: 小 / 嬉しさ: 人による（試して合わなければ消す類）**

## E. 遊び・見た目

### E-1. プレイリストカバーの自動生成 🎨

`playlist_upload_cover_image`（base64 JPEG）は生きている。アーティスト別プレイリストに
統一デザインのカバー（アーティスト名＋曲数＋テーマ色）を Pillow で描画して設定。
自動作成プレイリストが増えるほど「のっぺらぼうカバー」が並ぶ問題に効く。

- **工数: 中 / 嬉しさ: 中（開くたび目に入る場所なので体感は大きい）**

### E-2. GitHub プロフィールに音楽バッジ

profile README に「今月のトップアーティスト」「聴取時間」を nightly が SVG で更新。
コードを書く人間としてのプロフィールに、生活の実データが載る。

- **工数: 小（A-1 依存）/ 嬉しさ: 小〜中（遊び）**

### E-3. 年間ベストの自動編纂 🎁

12月に `Best of 2026` プレイリストを聴取ログから自動生成（再生回数×近時性で重み付け）。
Wrapped と違って**アルゴリズムが自分のもの**なので、重み付けをいじる楽しさがある。
A-2 の年次版として実装はほぼ共通。

- **工数: 小（A-2 依存）/ 嬉しさ: 大（年1回の風物詩になる）**

### E-4. 実家 Windows の local LLM は使わない（確認済み方針）

分類の最後の砦は Gemini のまま（キャッシュで到達自体が稀）。1日以上オフラインの
マシンを夜間バッチの依存に入れない。既決事項の再確認として記載。

## F. Claude / AI 組織との接続

### F-1. Spotify MCP で「音楽係 Claude」🤖

Claude（このセッションにも Spotify MCP が接続されている: 検索・再生中取得・プレイリスト作成）に
自然言語でプレイリスト操作を頼める。「今流れてる曲、Discovery に入れといて」
「雨の日の作業用に Western Musics から30曲選んで新しいプレイリスト作って」。
コードにする必要がない操作は会話で済ませ、**繰り返すようになった操作だけ nightly に昇格**させる、
という機能開発のじょうご（funnel）として使える。

- **工数: ゼロ（既にある）/ 嬉しさ: 使い方次第で大**

### F-2. 音楽担当エージェントの実験場

AI 組織構想（chief-of-staff から1体ずつ）の**最初の現場エージェント候補**としての
「音楽係」: リスクが低い（壊れても音楽）・毎日仕事がある・成果が聴いてわかる・
Issue チャネルが既に整備済み。D-1 の双方向 Issue はそのまま
エージェントとの協調プロトコルの雛形になる。壮大な話の、安全で楽しい練習台。

## やらない方がいいもの（先に潰しておく）

| 案 | 却下理由 |
|---|---|
| BPM/ムード別プレイリスト | `audio_features` が 403（実測）。Gemini でムード推定は可能だが精度と手間が見合わない |
| 歌詞ベースの分析・表示 | 公式歌詞 API なし（Musixmatch は有料 B2B）。著作権的にも保存はグレー |
| スキップ検知・完聴率 | API にイベントがなく `recently_played` からの推定は不正確。作っても信用できない数字になる |
| リアルタイム連携（聴いた瞬間に反応） | 常駐プロセスが必要になり「夜間バッチ+Issue」の簡潔な運用モデルを壊す。日次で困っていない |
| 他人へのレコメンド共有・SNS 化 | 個人の生活ツールという核から外れる。公開はダッシュボード（A-6）まで |

## 実装順の提案 — 複利で効く順

```
第1弾（すぐ・小粒で即効）
  B-1 新譜ウォッチ ＋ B-4 客演検知     ← 明日から毎日嬉しい
  A-1 聴取ログ蓄積                     ← 1日でも早く始めるほど資産になる（要スコープ再認証）
  D-2 週次ダイジェスト                 ← 以降の全報告の置き場

第2弾（基盤の上に楽しさを積む）
  A-2 月次リキャップ ＋ A-5 ヘビロテ
  D-1 Issue 双方向振り分け             ← 摩擦除去 + AI組織の実験
  C-1 重複検出 / C-2 灰色曲検知

第3弾（資産が貯まってから真価）
  A-3 タイムマシン / B-2 アーカイブ発掘 / E-3 年間ベスト / A-6 ダッシュボード
```

判断基準はシンプルに: **第1弾だけでも「新譜を逃さない・履歴が貯まり始める・週1の読み物が届く」
という3つの新しい日常が手に入る**。そこから先は、使ってみて欲しくなったものだけ作ればいい。
